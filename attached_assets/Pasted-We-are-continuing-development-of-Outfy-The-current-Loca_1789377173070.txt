We are continuing development of Outfy.

The current LocationPicker and GPS location flow are working correctly.

There is now one UX/data-quality issue we want to fix:

For Spain, the current region selector mixes Autonomous Communities and Provinces in the same list.

Examples of the problem:
- Catalonia / Cataluña
- Aragón
- Zaragoza
- Barcelona

These are not all the same administrative level.

For Outfy, when the selected country is Spain, we want the manual hierarchy to be:

Spain
→ Province
→ City

We DO NOT want to add an Autonomous Community selector.

GOAL — SPAIN SHOULD SHOW PROVINCES ONLY
==================================================

When:

countryCode === 'ES'

the region selector must represent PROVINCES only.

The user should NOT see a mixture of:

- Autonomous Communities
- Provinces

Do not show entries such as Cataluña / Catalonia or Aragón in the same selector as Zaragoza, Barcelona, Huesca, etc. if they represent a different administrative level.

==================================================
USE THE EXISTING DATASET
==================================================

Continue using the existing:

@countrystatecity/countries-browser

data.

Do NOT install another geographic dependency.

Do NOT hardcode a complete independent Spanish city database.

For Spain, derive the valid province list from the actual city data.

Recommended strategy:

1. Get all Spanish cities using the existing dataset.

2. Collect the unique `state_code` values actually referenced by those cities.

3. Get the available Spanish state/region entries from the existing dataset.

4. Keep only entries whose code is actually referenced by Spanish cities.

5. Deduplicate the resulting list.

6. Sort provinces alphabetically for display.

The important principle is:

The province selector should be based on the administrative codes actually used by the CITY records.

This avoids showing higher-level Autonomous Community entries that are not the region associated with individual city records.

If the actual library field names differ slightly from these names, inspect the current LocationPicker implementation and use its existing types/API.

Do NOT guess.
