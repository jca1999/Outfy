CURRENT DATABASE MODEL
==================================================

Existing tables:

public.activities
public.activity_members

Important existing behavior:

- creator automatically becomes an activity member
- creator role = 'organizer'
- organizer counts toward max_participants
- memberships use:
  primary key (activity_id, user_id)
- activity roles:
  organizer
  participant
- max_participants is NULL for unlimited activities
- status:
  active
  completed
  cancelled

Current API uses a privileged server-side Supabase client.

Therefore the new RPCs will be called ONLY from the trusted API server.

==================================================
GOAL
==================================================

Create safe database functions for:

1. joining an activity
2. leaving an activity

Joining MUST be safe when multiple users attempt to take the last available
place concurrently.

==================================================
RPC 1 — JOIN ACTIVITY
==================================================

Create a function with a clear name such as:

public.join_activity_as_user(
  p_activity_id uuid,
  p_user_id uuid
)

This function is intended ONLY for trusted server/service-role use.

It must NOT be callable by:

- PUBLIC
- anon
- authenticated

Explicitly REVOKE EXECUTE from all three.

Allow execution only through the server's privileged role as appropriate.

==================================================
JOIN — TRANSACTION / LOCKING
==================================================

The join operation must be atomic.

Inside the function:

1. Locate the target activity.

2. Lock the activity row using an appropriate row-level lock such as:

SELECT ... FOR UPDATE

This lock is important because concurrent joins for the same activity must
serialize before capacity is checked.

3. If the activity does not exist:
   return a clear result such as:

not_found

4. If activity.status is not 'active':
   return:

not_active

5. Check whether p_user_id is already in activity_members.

If already present:
- do NOT insert another row
- return:

already_member

This includes the organizer.

6. If participation_mode = 'limited':

Count CURRENT activity_members rows for that activity.

Remember:

the organizer already counts as one member.

If:

member_count >= max_participants

return:

full

without inserting.

7. Otherwise insert:

activity_id = p_activity_id
user_id = p_user_id
role = 'participant'

8. Return a successful result:

joined

==================================================
JOIN RESULT
==================================================

Return enough structured information for the future API to update the UI
without immediately performing another count query.

Prefer returning:

result
member_count
max_participants

Conceptually:

{
  result: 'joined',
  member_count: 2,
  max_participants: 5
}

For unlimited activities:

max_participants may be NULL.

When practical, return the CURRENT member count for:

- joined
- already_member
- full

Do not expose unrelated activity/user data.

==================================================
CAPACITY SAFETY
==================================================

The implementation must ensure this scenario is safe:

Activity:
max_participants = 2

Current members:
1 organizer

Two users attempt to join simultaneously.

Expected result:

- one request becomes joined
- member count becomes 2
- the other request receives full
- final membership count remains 2

Do NOT implement capacity checking only in application code.

The activity row lock must protect this invariant.

- authenticated

==================================================
LEAVE BEHAVIOR
==================================================

The function must:

1. Find the user's membership.

2. If no membership exists:
   return:

not_member

3. If membership role = 'organizer':
   DO NOT delete it.

Return:

organizer_cannot_leave

The organizer must not be able to accidentally remove the organizer
membership through this normal Leave action.

4. If role = 'participant':

Delete exactly that membership.

Return:

left

5. Return the updated member count where practical.

Do NOT cancel the activity.

Do NOT transfer organizer ownership.

Those are future organizer-management features.
