==================================================
ACTIVITY CONSTRAINTS
==================================================

Add sensible database CHECK constraints.

TITLE

Trimmed title must not be empty.

If the current Create Plan UI already defines a title maximum length, match it.

If it does not, use a reasonable initial limit of 120 characters.

DESCRIPTION

If the current UI already defines a maximum, match it.

Otherwise use a reasonable safety limit without making normal activity descriptions impractical.

CATEGORY / SUBCATEGORY

Store stable taxonomy IDs as text.

DO NOT store translated labels.

DO NOT create a PostgreSQL enum containing every taxonomy item.

Taxonomy evolution should not require a database enum migration.

LOCATION TYPE

Allowed:

physical
online

Physical activities:

- city must be present and non-empty

Online activities:

- physical location fields may be null
- online_platform remains optional

Do NOT require coordinates because manually entered cities may not have them yet.

Validate coordinates when present:

latitude between -90 and 90
longitude between -180 and 180

TIME

If ends_at is present:

ends_at must be greater than starts_at.

PARTICIPATION MODE

Allowed:

limited
unlimited

If limited:

max_participants must be >= 2

If unlimited:

max_participants must be NULL

IMPORTANT:
For this model, max_participants represents the TOTAL number of members in the activity, including the organizer.

COST TYPE

Allowed:

free
paid
each_own

For free:

estimated_cost must be NULL
currency must be NULL

For paid:

estimated_cost must be > 0
currency must be present and non-empty

For each_own:

estimated_cost and currency may remain NULL.

Do NOT restrict the database permanently to only EUR/USD.

Currency should be stored using an uppercase ISO-style code.

STATUS

Allowed:

active
completed
cancelled

No hard-delete UI behavior is being implemented yet.

==================================================
AUTOMATIC ORGANIZER MEMBERSHIP
==================================================

When an activity is created, its creator must automatically become a member with:

role = 'organizer'

Implement this at DATABASE LEVEL.

Prefer an AFTER INSERT trigger on public.activities.

The trigger must insert:

activity_id = NEW.id
user_id = NEW.creator_id
role = 'organizer'

Make this safe and deterministic.

If a SECURITY DEFINER function is used:

- set an explicit safe search_path
- schema-qualify important objects
- do not expose unnecessary execution permissions

The organizer invariant must not depend on the frontend remembering to make a second insert.

==================================================
RLS — ACTIVITIES
==================================================

Enable RLS on:

public.activities

Initial policies should support future authenticated access even though the current API uses a privileged server-side Supabase client.

READ

Authenticated users may read active activities.

Creators should also be able to read their own activities regardless of active/completed/cancelled state.

INSERT

Authenticated users may create an activity only when:

creator_id = auth.uid()

UPDATE

Authenticated users may update only activities they created.

Ensure ownership cannot be changed to another user.

DELETE

Do NOT create a normal authenticated hard-delete policy in this first version.

Cancellation will eventually be implemented by updating status.

==================================================
RLS — ACTIVITY MEMBERS
==================================================

Enable RLS on:

public.activity_members

READ

Create an initial sensible policy allowing authenticated users to read membership information for activities they are allowed to view.

Be careful to avoid RLS recursion.

JOIN

Authenticated users may insert ONLY themselves:

user_id = auth.uid()

and normal self-join must use:

role = 'participant'

A client must NOT be able to insert themselves as organizer.

The automatic activity-creator trigger is responsible for organizer membership.

LEAVE

Users may delete their own PARTICIPANT membership.

Do NOT allow the organizer membership to be removed using the normal self-leave policy.

ROLE CHANGES

Do NOT allow normal authenticated clients to arbitrarily change membership roles.

Do not add a broad UPDATE policy for activity_members.

==================================================
IMPORTANT CAPACITY NOTE
==================================================

Do NOT try to implement safe participant-capacity enforcement through simple RLS in this migration.

Concurrent joining will later require an atomic RPC/server operation.

The database should contain max_participants, but the real join operation will be implemented later.

==================================================
SECURITY ARCHITECTURE
==================================================

The current Outfy API uses a privileged server-side Supabase client.

This means server operations may bypass normal RLS.

That is expected.

RLS should still exist as defense in depth and for potential future authenticated direct access.

Do NOT:

- expose service-role credentials
- put Supabase admin keys in frontend code
- alter the existing authentication architecture
