PART 2 — SCROLL TO FIRST VALIDATION ERROR
==================================================

CURRENT PROBLEM:

On mobile, the Create Plan form is long.

If the user is near the bottom and presses:

"Revisar plan"

while an earlier required field is invalid, validation correctly prevents
continuing, but the user may not see the error.

This makes it appear as though the button/page did nothing or is still
loading.

Fix this.

==================================================
EXPECTED BEHAVIOR
==================================================

When the user presses Review Plan:

1. Run the EXISTING validation.
2. If there are no errors:
   -> continue to Review exactly as today.
3. If there are errors:
   -> identify the FIRST invalid field in visual/form order.
   -> smoothly scroll that field into view.
   -> focus the relevant form control when appropriate.

The user must immediately see:

- the field
- its error message
- what needs fixing

==================================================
ERROR ORDER
==================================================

Use the same visual order as the form.

For example:

1. title
2. category
3. subcategory
4. date
5. start time
6. end time
7. city when physical
8. max participants when limited
9. estimated cost when paid

Do not scroll to a later error if an earlier visible field is also invalid.

==================================================
SCROLL POSITION
==================================================

Use smooth scrolling.

Prefer behavior equivalent to:

scrollIntoView({
  behavior: 'smooth',
  block: 'center'
})

or another implementation that keeps:

- field label
- input
- error message

comfortably visible.

Do NOT scroll the input flush against the very top of the viewport.

This must work properly on mobile.

==================================================
FOCUS
==================================================

After identifying the first invalid field, focus its appropriate control when
possible.

Examples:

Title
-> title input

Category
-> category select

Date
-> visible editable date input

Start time
-> visible editable start-time input

City
-> city input

Max participants
-> number input

Cost
-> estimated-cost input

For radio/choice groups, focus a sensible first control or scroll to the
group container.

Do not open native date/time pickers automatically.

Focus must NOT trigger the calendar/time picker.
